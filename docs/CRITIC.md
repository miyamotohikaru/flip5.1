# 批評の手順（辛口審査）

この作品の完成条件は「AAA（RDR2 / Horizon / 最近の CoD の屋外シーン）のスクリーンショットと並べて、
どちらが本物のゲームか当てられないこと」。批評担当は制作担当とは別の目で、毎ラウンド次を行う。

## 撮る
```
node tools/shoot.mjs rN --all            # 12定点（shots/rN_<定点>.png）
node tools/shoot.mjs rN_m --shot golden --mobile
node tools/shoot.mjs rN_m --shot forest --mobile
python3 tools/sheet.py rN                # 一覧表 shots/rN_sheet.png
python3 tools/sheet.py --pair r(N-1) rN  # 前ラウンドとの並び
```

## 採点（定点ごと・10点満点）
| 観点 | 落第の例 |
|---|---|
| 光と大気 | 空がグラデーションの板／遠景が灰色一色／影が浮いている／夜が青いだけ |
| 材質 | ベタ塗り／タイル感／のっぺり／濡れ・雪・岩の質感が無い |
| 形 | 山が団子／木が円錐／草が板／岸線が硬い一本線 |
| 密度と自然さ | 一様な配置／群落が無い／人工的な繰り返し |
| 破綻 | 割れ目／ポップ／ジャギ／Zファイト／影のアクネ／水面のずれ |
| 仕上げ | ブルームで眠い／エフェクト感／色が安っぽい |
| 裏返し | 数式ビューが「ワイヤーフレーム表示」でしかない／正体が伝わらない／縁の波が美しくない |

各定点に「点数」「最も目立つ欠点（1つ）」「直し方の指示（担当モジュール名つき）」を書く。
合格は **全定点 9 点以上**、かつ携帯（mid）でも 7 点以上。

## ブラインド比較（最終ラウンド）
批評担当は、AAA の実写真的なスクリーンショットの記憶と本作の画を「どちらが本物のゲームのスクリーンショットか」
の問いで比べ、**必ずどちらかを選ぶ**。本作が選ばれない定点は不合格。理由を一行で。


## 定点を変えたときの記録（透明性のため必ず残す）

定点（`src/engine/core/params.ts` の `SHOTS`）は批評の物差しそのものなので、**変えたら理由を必ずここに書く**。
点を取りに行くための変更は禁止。「その構図が写真として成立していない」ときだけ動かす。

- **2026-09-03 `noon` / `cloudy` を移動。** 旧位置は太陽がカメラの真後ろ 23°にあり、
  影が物陰に隠れて「昼なのに落ち影が 1 本も無い」画になっていた（影担当が実測で確認。
  カスケードの配り方・`shadowMaxFar`・雲の影のどれを変えても 1px も変わらないことを検証済み）。
  写真として成立しない構図なので、木の近く・太陽が横から当たる向きへ移した。
  **影の仕組みは変えていない。** 併せて木が影を落とす距離（120m）を伸ばす作業を植生担当に依頼した。

- **2026-09-03（同日）`noon` / `cloudy` を元に戻した。** 批評ラウンド3の判定
  「理由は事実だが、影が無いと指摘された当のラウンドで物差しを動かすのは利益相反。
  しかも新しい2点は写真として旧2点より悪い（段ボールの木・裸の土）」を受け入れた。
  横から当たる構図は **`noon_side` / `cloudy_side` として別に追加**（定点は 12 → 14）。
  **教訓: 定点は「直せなかった言い訳」に使わない。物差しは固定したまま中身を直す。**

## 測り方の約束（**実際に間違えて覚えたこと**。指摘の前に必ず通す）

順に読む必要はない。**指摘を書く前に、下の該当する節に当てはまっていないかを 1 度確かめる。**
ここに並んでいるのは全部、批評か統合担当か担当のいずれかが**実際に間違えた**ものである。

## 明るさの測り方（2026-09-03 に食い違いが判明したので固定する）

**明るさは「表示線形」で測る。** sRGB の 0〜1 をそのまま読むと、同じ絵が別の数字になる。
批評ラウンド3で、批評が 0.047 と書いた画素をポスト担当が 0.50 と報告し、突き合わせたら
**批評＝線形・担当＝sRGB** で、同じ絵を別の単位で読んでいただけだった（式まで一致した）。

- 測る場所: 画面の下 1/3 の中央値（近景）
- 彩度: 全画面の `(max−min)/max` の平均
- **目安（表示線形）**: 18% グレーカード = 0.18 ／ 90% 白 = 0.90 ／ **日なたの草 = 0.13〜0.20**
  （草の反射率は輝度換算 0.15〜0.20。適正露出の写真ではグレーカードのすぐ下に落ちる）
- **「日なたの草 0.32〜0.45」は誤り**（拡散白色面の値を草に当てた数字）。ラウンド3でこの目標が出たが、
  ポスト担当が根拠つきで 0.11〜0.21 に置き直した。**批評はこの根拠を読んでから採点すること。**
  ただし「暗すぎて草が読めない」（golden 0.045）は本物の欠点で、これは直した。

### 色の判定に R−B を使わない（2026-09-03）

「濡れた砂が赤紫」の指摘を追ったところ、実際には **R−G はどこでも負（緑優勢）** で赤紫は出ていなかった。
R−B が +25 に見えたのは草の青が低いためで、**R−B 単独では「黄緑」と「赤紫」を区別できない**。
色みの判定は **R−G か色相**で行う。明るさは表示線形（上の節）。

### 「細かすぎてジャギになっている」と思ったら 3 倍で描いて縮小する（2026-09-04）

岸の彗星形のにじみを、批評も担当も **3 ラウンド続けて「幅 1m の帯が 1.5km 先で 1 画素を切るからジャギになる」と読み違えた**。
R6 では批評が犯人でない 4 行を名指しし、担当が 1 行ずつ切って「どれも違う」と返している。

決め手は **`--dpr 3` で描いて 1600×900 に縮小すること**。3 倍で描けば標本化のジャギは 1/3 に落ちるはずなので、
**形が変わらなければジャギではない**。実際に std は 11.10 → 9.77 でしか下がらず、形はそのままだった。
正体は「細さ」ではなく**幾何**で、視線とほぼ平行な対岸では幅 1〜3m の浜が画面では奥行き方向 200 画素の舌になっていた。

手順として固定する:

1. `?dbg=` でどの担当かを切り分ける（見えた場所と犯人は違う）。
2. `?tdbg=` などの層別の可視化で、**どの層に形が出るか**を見る（この件はマスクの層に出た）。
3. **`--dpr 3` で描いて縮小し、形が変わるかを見る。** 変わらなければ標本化の問題ではない。
4. そこまでやってから行を名指しする。**名指しの前に切り分ける。**

### 明るさは「比」で見る。露出では比は変わらない（2026-09-04）

`noon_side` が明るすぎる件を 2 ラウンド「露出を下げろ」と書いてきたが、それは半分しか当たっていなかった。
**露出は近景と空を同じだけ動かすので、近景 ÷ 空の比は 1 も変わらない。**
実際、ポスト担当が 0.2612 → 0.2142 まで下げても、比は 106.3% のままだった。

`dbg=noveg`（草と木を切る）で測ると比は **126.0%** に上がる。**明るいのは地面そのもの**だった。
晴天の昼に日なたの草地が空より明るいことは物理的に無い（青空 5000〜8000 cd/m² に対し、
日なたの緑の草地は 2000〜3000 cd/m²）。つまりアルベドが高すぎる。

**手順として固定する:**

1. 明るさを指摘する前に、**近景 ÷ 空**を出す。比が高ければ**アルベドか照明**であり、露出では直らない。
2. 比が妥当で絶対値だけがずれているときに、はじめて露出の話をする。
3. **担当に渡す合否条件は、できるかぎり比で書く。** 比は後から誰が露出を動かしても揺れないので、
   「直したのに別の担当の変更で数字が動いた」という水掛け論が起きない。

測り方（統一する）:

```
sRGB 8bit → 表示線形:  x/255 を、x≤0.04045 なら /12.92、そうでなければ ((x+0.055)/1.055)^2.4
輝度 Y = 0.2126R + 0.7152G + 0.0722B の中央値
近景 = 下 1/3 の中央 50%（W/4〜3W/4、2H/3〜H）  ／  空 = 上 30%
```

### 「遠いからジャギ」の前に、その画素が地面をどれだけ覆っているかを測る（2026-09-04）

岸の彗星形のにじみは、**批評も統合担当も距離を取り違えていた**。
批評は 3 ラウンド「1.5km 先の対岸の浜」と書き、私（統合）はその見立てで担当に 1 行の修正を渡した。
地形担当が `?tdbg=13`（距離帯）を足して測ると、その矩形は **9〜45m**、つまり**画面の下 1/3 の足元**だった。
カメラ高 1.7m・pitch −2°・fov 72° から解析でも一致する（12m → y=576、45m → y=502）。
1.5km の対岸は同じ矩形の **35 画素上**にある。だから 90m から効く `shoreFar` はこの数字を 1 画素も動かせない。

本当の原因は `?tdbg=14`（画素の足跡）で分かった。**浅い角度で見る地面では、1 画素が奥行き方向にだけ潰れて
12〜50cm を覆う。** λ0.4〜0.9m の模様は標本化できず、一方向に伸びた縞になる。
**dpr 3 で形が変わらなかったのはこのため**で（圧縮比が 10:1 以上なので 3 倍では足りない）、
前の節の「3 倍で描いて縮小する」だけでは切り分けられない場合があるということでもある。

**手順に足す:**

1. 矩形を指摘するときは、**その矩形が何 m の地面かを先に測る**（`?tdbg=13`）。「遠景に見える」は当てにならない。
2. **1 画素が地面で覆う長さ**（`length(fwidth(xz))`、`?tdbg=14`）を見る。模様の波長がそれより短ければ、
   距離ゲートでは守れない。**ミップ相当のゲート**（足跡で切る）が要る。
3. **相反する要求を同じ画素に出していないか確かめる。** この件では「岸の std を 4 以下に」と
   「15〜110m の地面に情報を入れよ（std 12〜18）」が**同じ画素**を指していた。

### 訂正: 「近景 ÷ 空 は 30〜50%」は私（統合担当）の誤りだった（2026-09-04）

上の節で私は「実写では 地面 ÷ 空 が 30〜50%」と書いて担当に渡した。**これは間違いである。**
写真を見た印象（空は明るく、草は暗い）を輝度の比だと思い込んだが、実際には**明るさではなく明度と色みの差**である。

輝度で計算するとこうなる:

- 日なたの緑の草（アルベド 0.20、水平面照度 100,000 lx）の輝度 = 0.20 × 100000/π ≈ **6,400 cd/m²**
- 晴天の天頂の空 = **2,000〜4,000 cd/m²**（地平寄りはその 2〜3 倍）

**つまり晴天の昼は、日なたの草地のほうが天頂の空より明るい。** 「地面が空より明るいのは物理的にありえない」
と私が書いたのも誤りだった。空担当が実測で示した内訳:

- 間接光の内訳: 空 12.3% / 太陽 87.9%（物理の予測 9.9% と一致）＝ 二重計上なし
- **E⊥ / L天頂 = 43.3 sr**（地球の晴天は 25〜50 sr）＝ 立体角も積分も正しい
- `ρ/π·E·cosθ` の予測 0.0895 に対し実測 0.0879（誤差 1.8%）＝ π の抜けもない

**教訓: 「物理的にありえない」と書く前に、その物理を数字で出す。** 出せないなら「実写と違って見える」と書く。
比を合否条件にするのは正しい（露出に左右されないので）が、**その比の目標値も同じ厳しさで裏を取る。**

### `storm` は撮影ごとに ±0.07 段揺れる（2026-09-04）

同じ条件・同じビルドで撮り直しても、`storm` の近景の明るさは **±0.07 段**動く（実測 0.0316 / 0.0317 / 0.0318 に対し、
別の回は 0.0302）。時間を止めていても、嵐の雲と閃光の位相が撮った瞬間で違うため。

**この定点の明るさで前後を比べるときは、2 回撮って中央値を取るか、揺れの幅を織り込む。**
0.07 段以内の差を「効いた／退行した」と書かない。`storm_live` と `storm_bolt` も同じ。

### 物差しが「別の直し方」で満たせてしまうことがある（2026-09-04）

「中景の木がなめらかな円錐に見える」を **3×3 の局所標準偏差**（のっぺりした画素の割合）で測っていたが、
**殻にノイズを乗せれば、面が詰まったままでも合格してしまった。** 2 ラウンド続けて同じ退行を見逃した。

**物差しは「直したい性質そのもの」を測る。** この件で正しかったのは**すかし率**:

```python
sky  = (B > G+8) & (B > R+8)          # 空を背にした所だけ見る
tree = (G > R+4) & (G > B+4)
filled = scipy.ndimage.binary_fill_holes(tree)   # 樹冠の輪郭を埋める
holes  = filled & ~tree & sky                    # 樹冠の内側に見えている空
すかし率 = holes.sum() / filled.sum() * 100
```

`forest` (380,20)-(900,470) で **3.09% → 1.45%**（半分）と一発で出た。局所 std では 10.44 → 9.74 しか動かない。

**教訓: 合否条件を書くときに「これを別のやり方で満たせないか」を 1 度考える。**
満たせるなら、その物差しは目的を測っていない。

### 測る矩形が、ふだや HUD に覆われていないか確かめる（2026-09-04）

裏返しの等高線の比を (300,280)-(700,420) で測っていたが、**この矩形は「地形 TERRAIN」のふだが半分を覆っている。**
ふだの線文字が等高線と同じ明るさで混ざるので、比が実際より小さく出る（画素数で 4.00 対 5.00 の差）。
**等高線を測るときはふだの外の列（x=300〜360）で測る。**

一般則: **矩形を決めたら、その矩形に世界以外のもの（ふだ・HUD・照準・数式パネル）が入っていないか 1 度目で見る。**
`?nohud=1` で撮り直して数字が変わるなら、それは UI を測っている。
